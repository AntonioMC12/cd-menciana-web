# Auditoría y plan SEO · CD Menciana

Fecha: 5 de octubre de 2026. Ámbito: web pública `https://cdmenciana.es/`, repositorio Astro y CMS público. La revisión combina respuestas HTTP de producción, HTML inicial, API de publicaciones y código fuente. No se dispone de acceso a Search Console, analítica ni datos de campo de Core Web Vitals; no se atribuyen cifras de tráfico o posiciones.

## Resumen ejecutivo

La web respondía correctamente en HTTPS y redirigía `http` y `www` al dominio principal. Existían `robots.txt`, sitemap y una página 404. Los principales problemas comprobados eran editoriales: noticias y galerías se insertaban solo tras ejecutar JavaScript, todas las noticias compartían una URL de detalle con `?slug=` y el mismo canonical, y el sitemap anunciaba esas páginas genéricas en lugar de cada publicación. El calendario también carecía de partidos en el HTML inicial. El enlace de la portada a `#proximo-partido` no tenía destino. Estas incidencias perjudicaban la identificación y el descubrimiento de contenido específico.

Se han generado páginas estáticas para las publicaciones reales del CMS, con URL, título, descripción, imagen social y canonical propios; se han añadido datos estructurados respaldados por contenido visible; se ha limpiado el sitemap; el calendario muestra una copia inicial verificada, y se ha corregido el ancla. La publicación editorial se incorpora mediante reconstrucción programada cada seis horas. El calendario deportivo sigue actualizándose desde la API sin reconstrucción.

## Hallazgos y evidencia

| Prioridad | Hallazgo comprobado antes del cambio | Acción |
| --- | --- | --- |
| Alta | `/noticias/` entregaba en el HTML inicial solo «Cargando noticias…». | Listado y portada renderizados en compilación desde publicaciones reales. |
| Alta | `/noticias/detalle/?slug=victoria-derbi-cd-santaella-2-0` devolvía título genérico y canonical `/noticias/detalle/`. | URL individual `/noticias/victoria-derbi-cd-santaella-2-0/`, metadatos propios, ruta anterior con `noindex` y redirección en navegador. Igual para galerías. |
| Alta | El sitemap incluía rutas genéricas de detalle y no los artículos reales. | Sitemap de rutas canónicas generadas; exclusión de 404 y detalles antiguos. |
| Media | El calendario cargaba los encuentros solo con JavaScript. | Copia inicial verificada del primer equipo en HTML; la API conserva la actualización dinámica. |
| Media | El enlace «Próximo partido» apuntaba a un ancla inexistente. | Ancla añadida. |
| Media | La portada describía poco el club y decía «ciudad» para Doña Mencía. | Texto local más explícito y terminología correcta. |
| Oportunidad | No hay dirección ni correo institucional confirmados. | Se evita inventarlos en la web o en `Organization`; confirmar datos antes de ampliar contacto y perfiles locales. |
| Sin verificar | Cobertura/indexación, CTR, consultas, CWV reales, enlaces entrantes y ficha de Google Business Profile. | Medir con acceso a Search Console, analítica, PageSpeed/CrUX y cuentas verificadas. |

Las redirecciones HTTP→HTTPS y `www`→dominio principal se comprobaron como 301; una URL inexistente respondió 404. La existencia de un sitemap no garantiza indexación.

## Arquitectura de búsqueda e intención por página

| Página | Intención principal | Contenido que debe mantenerse actualizado |
| --- | --- | --- |
| `/` | Encontrar el club de fútbol sala de Doña Mencía y acceder a lo esencial. | Identidad, equipos, siguiente partido, resultados, noticia reciente. |
| `/club/` | Conocer al CD Menciana Apaga y Vámonos F.S. | Historia, valores y datos institucionales confirmados. |
| `/equipos/` | Consultar categorías y plantilla. | Equipos reales, jugadores, dorsales y posiciones verificadas. |
| `/calendario/` | Saber cuándo, dónde y contra quién juega cada equipo. | Jornada, competición, fecha, hora, pabellón, estado y marcador oficiales. |
| `/noticias/` y `/noticias/[slug]/` | Leer actualidad y crónicas concretas. | Titular específico, entradilla, cuerpo, fecha, portada y alt. |
| `/galerias/` y `/galerias/[slug]/` | Ver fotografías de una actividad concreta. | Título, descripción, fecha y pies/alt descriptivos. |
| `/patrocinadores/` | Identificar empresas y entidades colaboradoras. | Nombres, logos y enlaces facilitados por el club. |
| `/contacto/` | Encontrar vías reales para hablar con el club. | Solo contactos confirmados. |

No se recomiendan páginas creadas solo para captar variantes de palabras clave. En noticias y galerías, el panel editorial ya recoge título, resumen y portada; las fotos de álbum tienen texto alternativo. Los tres primeros campos alimentan el HTML y las etiquetas sociales, mientras el texto alternativo se muestra en la galería. Conviene que cada título describa el hecho concreto, que el resumen aporte contexto y que el alt describa la foto sin repetir palabras clave mecánicamente. Revisar crónicas antiguas que digan «próximo» para que su fecha evite confusiones.

## SEO técnico implementado

- HTML inicial con noticias, galerías y una copia verificable de partidos del primer equipo.
- Una URL estable por artículo y álbum, con `title`, `description`, canonical, Open Graph y Twitter Card individuales.
- `Organization` en portada, `BreadcrumbList` en detalles y `NewsArticle` en noticias, usando solo hechos presentes en la web. No se añadió `Event` a la lista de partidos: Google exige páginas de evento individuales con datos precisos para ese resultado enriquecido.
- Sitemap solo de páginas canónicas generadas. Se omite `lastmod` porque no existe una fecha de modificación fiable para todas las páginas.
- Reconstrucción programada del sitio para descubrir publicaciones nuevas; error de compilación si falla un CMS configurado, en vez de publicar listas vacías.
- Los detalles antiguos con `?slug=` usan redirección JavaScript y `noindex`. GitHub Pages no ofrece una regla 301 dependiente del parámetro de consulta; si se incorpora un proxy/edge, convertir estas rutas en 301 reales.

## SEO local y autoridad

Confirmar nombre legal, dirección de atención al público, teléfono, correo, horarios y titularidad de perfiles. Si existe una ubicación elegible y verificable, completar o reclamar el Perfil de Empresa de Google con esa información y enlazar la web. Mantener nombre y contacto consistentes en perfiles sociales, RFAF, ayuntamiento y patrocinadores. Solicitar enlaces editoriales pertinentes desde la federación, entidades locales, competiciones y colaboradores cuando publiquen contenido sobre el club. No comprar enlaces ni crear directorios masivos. Las redes sociales oficiales ya figuran en la web y en `sameAs`; no se inventó ubicación ni horario.

## Validación y límites

`npm run check`: 65 archivos, 0 errores/avisos. `npm test`: 11 pruebas aprobadas. `npm run build` con el CMS público configurado generó las rutas reales del artículo y álbum publicados y un sitemap sin páginas genéricas. Se comprobó el HTML local de la lista y del artículo, incluidos título, canonical, cuerpo visible y JSON-LD. La disponibilidad de la API del CMS sigue siendo requisito para el build de producción. La tarea programada de GitHub Actions no es instantánea y puede sufrir retrasos.

No se dispone de Chrome DevTools MCP en este entorno ni de datos de CrUX/Search Console. Por tanto, no hay puntuaciones Lighthouse o Web Vitals atribuibles a la web. Las verificaciones de responsive y teclado deben repetirse tras cada cambio visual importante; no deben sustituirse por una puntuación sintética inventada.

## Plan 30 / 60 / 90 días

**0–30 días.** Publicar los cambios, enviar el sitemap en Search Console, inspeccionar portada, calendario, artículo y álbum; revisar cobertura, canonicals y errores. Confirmar datos de contacto y responsable de la ficha local. Definir una pauta editorial de título, resumen, fecha y alt por publicación. Medir CWV en móvil y escritorio con herramientas de campo o laboratorio disponibles.

**31–60 días.** Publicar crónicas, previas y noticias útiles según actividad real; enlazar internamente equipos, calendario y artículos relacionados. Evaluar páginas individuales de partidos solo si hay datos oficiales persistentes suficientes para mantenerlas. Completar perfiles locales verificables y enlaces de colaboradores. Priorizar problemas de LCP/INP/CLS según mediciones, especialmente imágenes y scripts.

**61–90 días.** Comparar consultas, clics, impresiones y CTR por página en Search Console; revisar las páginas con impresiones pero baja interacción; actualizar información desfasada. Analizar referencias de calidad y búsquedas de marca/locales. Mantener vigilancia sobre errores de CMS, build y sitemap.

## Medición propuesta

En Search Console: propiedad de dominio, sitemap, páginas indexadas/excluidas, consultas de marca y no marca, consultas locales, clics, impresiones, CTR y posición con comparación mensual. Segmentar `/noticias/`, `/galerias/`, `/equipos/` y `/calendario/`; anotar fechas de publicación y cambios. En analítica, medir navegación hacia calendario, noticia, equipos, patrocinadores y redes sin recolectar datos personales innecesarios. Para rendimiento: LCP, INP y CLS de campo por plantilla y dispositivo; complementar con pruebas reproducibles de laboratorio. Definir línea base tras el despliegue y evaluar tendencias durante al menos 28 días; no atribuir causalidad a una sola modificación.
